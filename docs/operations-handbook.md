# Fenxiao 运营使用手册

## 1. 适用范围
这份手册面向日常运营 / 风控 / 客服排查人员，用于说明当前 Fenxiao Web Console 可以做什么、怎么做、什么情况下不要乱点。

---

## 2. 当前后台可做的事

### 2.1 登录与查看
- 后台 session 登录
- 运营概览查看
- 奖励列表分页查询
- 风险事件分页查询
- 关系链查询
- 最近处理记录 / 审计列表查看

### 2.2 风险事件处理
当前支持 4 个动作：
- `处理`
- `忽略`
- `冻结用户`
- `解冻用户`

当前前端交互已经升级为：
- 每条风险事件单独填写处理备注
- 执行动作前二次确认
- 动作成功后自动刷新奖励 / 关系链 / 最近处理记录

所有动作都会写入审计日志，并带上：
- 目标风险事件
- 动作名
- 处理备注
- 操作时间

## 3. 页面说明

### 3.1 奖励查询
适合查：
- 某个用户有没有奖励
- 某段时间奖励状态是否异常
- 风控后奖励有没有进入 `RISK_HOLD`

建议筛选项：
- 受益用户 ID
- 奖励状态
- 开始时间 / 结束时间
- 页码 / 每页条数

### 3.2 风险事件运营页
适合查：
- 某用户是否被打到风险事件
- 风险事件是待处理还是已忽略/已处理
- 风险动作是否已经执行

建议筛选项：
- 用户 ID
- 风险状态
- 开始时间 / 结束时间
- 页码 / 每页条数

当前操作方式：
- 先筛出事件
- 在单条事件卡片里填写本次备注
- 再点击对应动作进入确认框

### 3.3 关系链查询
适合查：
- 用户上级关系是否正确
- 用户当前关系是否被锁定
- 风险动作后关系状态是否发生变化
- 是否需要人工修正一级上级关系

如果确认关系绑定错了，当前后台已经支持：
- 人工修正一级上级用户 ID
- 留空后保存，将该用户设为根关系
- 提交前查看 before / after 预览
- 自动写 relation 模块审计日志

注意：
- 已锁定关系不能手工修正
- 不要把用户改到自己的下游链路里，避免形成循环关系
- 修正前建议先写清备注，方便后续复核

### 3.4 最近处理记录
适合查：
- 最近是谁处理了什么风险
- 有没有误操作
- 某个动作是否真的落库
- 人工关系修正是否已经写进 relation 审计

## 4. 风险动作说明

### 4.1 处理
适用于：
- 该风险已经确认，需要留档关闭
- 不需要进一步冻结/解冻，仅做处理完成标记

注意：
- 只允许对 `PENDING` 风险事件执行

### 4.2 忽略
适用于：
- 明确判断是误报 / 假阳性
- 该风险事件不应再触发运营动作

注意：
- 只允许对 `PENDING` 风险事件执行
- 被忽略的风险事件，不能再拿来冻结用户

### 4.3 冻结用户
适用于：
- 已确认该风险需要进入风控处理
- 需要让相关奖励进入风险挂起状态

执行后会联动：
- 用户状态转为风险态
- 风险事件进入已处理
- 相关奖励进入 `RISK_HOLD`
- 最近处理记录新增一条审计

注意：
- 只允许对 `PENDING` 风险事件执行
- 不要把“待观察”直接当成冻结依据
- 冻结前建议填写清楚处理备注

### 4.4 解冻用户
适用于：
- 已确认之前冻结为误判
- 或人工复核后决定恢复正常状态

执行后会联动：
- 用户恢复正常态
- 风险挂起奖励恢复为 `FROZEN` 或 `AVAILABLE`
- 最近处理记录新增一条审计

注意：
- 只有在系统识别到该用户确实存在风险挂起奖励时才允许解冻
- 不要对未冻结用户反复点击解冻

## 5. 推荐排查路径

### 场景 A：用户说奖励不见了
1. 先查奖励列表
2. 看状态是否为 `RISK_HOLD`
3. 再查风险事件
4. 如果命中风险事件，再决定是处理、忽略还是解冻
5. 最后看最近处理记录，确认动作是否落地

### 场景 B：用户说关系链异常
1. 查关系链
2. 看当前锁定状态
3. 如果伴随风险事件，再查风险列表
4. 必要时结合最近处理记录确认是否有人做过冻结/解冻
5. 如果确认一级上级绑错，且关系仍未锁定，再做人工修正并补备注

### 场景 C：复核一个风险事件
1. 先看风险详情和时间
2. 再看奖励状态是否已被联动影响
3. 决定是：处理 / 忽略 / 冻结 / 解冻
4. 填写简短但明确的备注

---

## 6. 处理备注建议
建议备注尽量短，但要包含判断依据。推荐格式：
- `人工复核通过，误报忽略`
- `确认异常收益，执行冻结`
- `用户申诉通过，恢复正常`
- `仅留档，无需进一步动作`

不建议只写：
- `已处理`
- `看过了`
- `ok`

---

## 7. 当前边界
当前这版已经是运营可用 MVP，但仍然有边界：
- 还没有更细的后台权限模型
- 还没有动作审批流
- 已有 Linky 适配入口、基础签名校验、时间窗防重放、webhook 日志落库，以及运营后台直接回看 webhook / replay record 的最小排查台
- 还没有更复杂的风控规则编排

所以当前使用原则是：
> 先解决日常排查与基础处置，不把后台流程做过重。

## 8. 上线前最小检查清单

### 8.1 用户端闭环
- 邀请码页能生成邀请码，并能通过手机号验证码登录保存用户 session。
- `/api/distribution/auth/phone-codes` 不回传验证码明文；重复发送未过期验证码返回 429。
- 收益页可看到：三层裂变人数、业务二/三/四级收益汇总、团队本周/上周钻石收入、奖励明细、提现历史。
- 用户发起提现申请后，提现历史能自动刷新并展示申请状态。
- 绑定 Linky ID 失败时，页面能提示对应公会邀请码，避免用户不知道该加入哪个公会。

### 8.2 运营后台闭环
- 后台能正常登录，后台 session / token 不在日志或页面明文暴露。
- 奖励查询、风险查询、关系链查询、最近处理记录均可返回数据。
- 风险动作能执行，且动作后奖励 / 关系链 / 最近处理记录会联动刷新。
- 提现申请列表可填写操作人 ID、操作角色、审批备注，并对待处理申请执行通过 / 拒绝。
- 提现审批 / 拒绝后，审计记录里能看到真实 operator payload。
- 公会配置管理可查询与保存上级用户对应的 Linky 公会 ID / 公会邀请码 / 启用状态。
- 公会周报可按周期返回注册用户、收入、分佣聚合结果，并可导出 CSV。

### 8.3 Linky 与公会归属闭环
- Linky 入口至少验证 `X-Internal-Token`、`X-Linky-Timestamp`、`X-Linky-Signature`。
- Linky webhook 日志能查到 signature / replayWindow / replayRecord / requestStatus 结果。
- 批量刷新全部 Linky 资格时，单账号失败不阻断整批；后台能看到成功 / 失败数量和失败明细。
- 定时刷新任务已启用或已明确关闭；上线环境需确认调度间隔、失败告警与重试策略。
- 注册资格按 Linky ID 对应公会归属判断；注册成功后的收益归属按邀请码关系判断。

### 8.4 上线配置与安全
- 真实 SMS provider 已配置 endpoint、app key、template、signature 等必要参数；文档和日志只写字段名或 `[REDACTED]`，不写真实凭据。
- `SmsSender` 真实实现已完成发送失败处理；默认 `LoggingSmsSender` 仅用于本地 / 测试 / 未接 provider 场景。
- 后台 session、用户 token、Linky internal token、数据库连接串、第三方后台账号密码均已按环境变量或安全配置注入。
- CORS、公网域名、HTTPS、回调地址、前端 API base URL 已按目标环境配置。
- 数据库迁移、备份、回滚方案已确认；导出报表不会泄露超出运营需要的敏感字段。

### 8.5 技术验证
- 前端定向测试通过：`npm test -- --run src/api.test.ts src/App.test.tsx`。
- 前端全量测试通过：`npm test -- --run`。
- 前端 build 通过：`npm run build`。
- 后端关键 controller / service 定向测试通过。
- 后端全量测试通过：`mvn -q test`。

## 9. MVP 最终验收矩阵

> 用途：上线 / 交付前按 11 项完整产品缺口逐项确认。状态分为：`已完成`、`需上线配置`、`仍有产品边界`。

### 9.1 已完成，可进入验收

| # | 验收项 | 当前完成态 | 验收方式 |
|---|---|---|---|
| 1 | 手机号注册登录体系 | 用户端已支持手机号验证码登录；后端发码不回传验证码、6 位随机码、未过期重复发码 429；短信发送已抽象为 `SmsSender` | 在邀请码页获取验证码并登录；检查响应不含 `verificationCode`；重复发码返回 429 |
| 2 | 邀请码 / 上级到 Linky 公会映射 | 后端已有公会配置落库、查询、保存、启停；运营后台已有公会配置管理入口 | 后台查询 / 保存一条上级用户对应的 Linky 公会 ID 和邀请码 |
| 3 | 绑定 Linky ID 时按上级对应公会校验 | 后端按上级公会配置校验 Linky ID 公会归属 | 用不同公会 Linky ID 绑定，确认错误公会被拒绝 |

| 5 | Linky ID 批量 / 定时刷新 | 已有批量刷新入口、失败明细、失败状态持久化、定时刷新调度器 | 后台点击批量刷新，确认成功 / 失败计数和失败明细；检查调度配置 |
| 6 | 用户端三层裂变人数 | 收益页已展示一级 / 二级 / 三级下级人数和有效人数 | 用有下级链路的账号打开收益页，核对三层人数 |
| 7 | 用户端二/三/四级收益 | 收益页已展示业务二级 / 三级 / 四级收益汇总与明细数量，明细使用业务层级文案 | 打开收益页，核对汇总金额、明细数量和业务层级标签 |

| 10 | 后台提现处理审计 | 后台提现列表支持通过 / 拒绝，并透传 operatorId / operatorRole / remark 到审计 | 对待处理申请执行通过 / 拒绝，检查审计记录操作人字段 |
| 11 | 公会规则配置与周报 | 公会配置管理与公会周报 API/UI 已接入，周报不再返回 0 占位，CSV 复用真实聚合 | 后台查询公会周报并导出 CSV，核对注册用户 / 收入 / 分佣聚合 |

### 9.2 需上线配置后才能正式开放

| 配置项 | 必须确认的内容 | 未完成风险 |
|---|---|---|
| 真实 SMS provider | endpoint、app key、template、签名、发送失败重试 / 告警；生产环境使用真实 `SmsSender` 实现 | 当前默认 `LoggingSmsSender` 只能作为本地 / 测试占位，不能给真实用户收码 |
| 后台账号 / session | 后台登录凭据、session 过期策略、操作人来源、权限分工 | 凭据泄露或多人共用账号会削弱审计可信度 |
| 用户 token | `X-Distribution-Token` 的签发、过期、刷新、前端存储策略 | token 过期 / 泄露会影响用户端访问安全 |
| Linky internal token 与签名 | `X-Internal-Token`、timestamp、signature、时间窗、防重放窗口 | webhook 被伪造、过期请求被接收或重复事件误处理 |
| 公会后台账号 | 各公会后台账号密码的安全注入与访问边界 | 人工核验 / 后续自动核验无法稳定执行 |
| 域名与回调地址 | HTTPS、公网域名、CORS、Linky 回调 URL、前端 API base URL | 页面或 webhook 在正式环境不可访问 |
| 数据库与迁移 | 生产库连接、迁移顺序、备份、回滚、导出权限 | 上线数据不可恢复或迁移失败 |
| 日志与脱敏 | 验证码、token、密码、连接串、第三方密钥只允许字段名或 `[REDACTED]` | 敏感信息进入日志 / 文档 / 报表 |

### 9.3 仍有产品边界，建议作为上线后迭代

| 边界 | 当前口径 | 建议后续迭代 |
|---|---|---|
| 后台细粒度权限 | 当前可支撑 MVP 运营，但不等于完整权限中心 | 补多运营账号、RBAC、账号管理与权限审计 |
| 短信风控 | 已有重复未过期验证码限频，但还不是完整反刷体系 | 补 IP / 设备 / 手机号维度频控、错误次数锁定、发送告警 |
| 公会自动核验深度 | 已有 Linky 资格刷新与失败持久化，复杂后台自动化仍依赖目标后台可访问性 | 补公会后台自动登录 / 抓取流程的稳定性与失败重试 |
| 周报维度 | 当前覆盖注册用户、收入、分佣聚合与 CSV | 补更多周期选择、运营负责人维度、异常数据标记 |
| 风控规则编排 | 当前是基础事件处理、冻结 / 解冻与审计闭环 | 后续可补规则配置台、审批流、批量处理 |
| 报表与对账 | 已有提现导出、公会周报、Linky replay / webhook 排查 | 后续补财务对账总表、差异标记、批量导出 |

### 9.4 最小上线验收顺序

1. 先用测试账号跑通用户端：手机号登录 → 绑定 Linky ID → 查看收益页 → 发起提现 → 查看提现历史。
2. 再用运营账号跑通后台：登录 → 查询奖励 / 关系 / 风险 → 处理风险 → 审批提现 → 查看审计。
3. 再跑 Linky / 公会链路：webhook 入账 → replay 防重 → 批量刷新 Linky 资格 → 查询公会周报 → 导出 CSV。
4. 最后做配置核对：SMS、token、签名、域名、CORS、数据库迁移、日志脱敏。
5. 技术验收必须保留最近一次通过记录：前端定向 / 全量 / build，后端关键定向 / 全量测试。
