# 分销功能全量需求整理（来自业务脑图）

> 来源：2026-05-12 用户提供的“分销功能”脑图。
> 目的：把脑图口径沉淀为 Fenxiao 项目的全量验收范围，后续研发、验收、日报和 Lark 文档都按此口径对齐。

---

## 1. 总体结构

分销功能分为两端：

1. 用户端
2. 公会端

用户端负责注册、绑定 Linky、生成邀请码、查看裂变人数/收益、发起提现。

公会端负责规则配置、数据爬取、查看提现/裂变报表。

---

## 2. 用户端需求

### 2.1 注册分销系统 / 登录绑定

- 用户通过网址进入分销系统。
- 支持手机号注册。
- 注册时必须输入分销邀请码。
- 注册后完成分销系统登录与绑定。

验收点：
- 对外注册入口不能允许空邀请码注册。
- 邀请码必须真实存在，才能建立上下级关系。
- 后续如接手机号登录，需要手机号唯一、验证码/密码/OTP 等登录机制。

---

### 2.2 下载注册 Linky 并绑定 ID 到分销系统

用户流程：

1. 新用户下载并注册 Linky。
2. 在 Linky 内绑定 Linky 邀请码。
3. 回到分销系统输入 Linky ID。
4. 分销系统后台查询验证 Linky ID。
5. 系统校验该 Linky ID 是否属于上级对应的公会。
6. 如果查询不到，则默认未绑定公会，并弹窗提醒用户填写对应 Linky 公会邀请码。
7. 每个分销 ID 只能绑定唯一 Linky ID。

验收点：
- Linky ID 唯一。
- 分销用户与 Linky ID 一对一。
- 查询不到时，用户侧必须有明确提示，不只是后台拒绝。
- 提示里要包含“对应 Linky 公会邀请码”或获取入口。

---

### 2.3 Linky ID 公会校验规则

核心规则：

- 用户输入 Linky ID 后，系统后台查询验证。
- 查询该 ID 是否属于“上级对应的公会”。
- 查询命中且归属正确时，允许绑定 / 注册。
- 查询不到时，默认未绑定公会。
- 查询不到后，弹窗提醒用户填写对应 Linky 公会邀请码。
- 所有 ID 的公会归属，最终根据爬取数据确认。

重要口径：
- 公会归属用于注册/绑定准入。
- 邀请码关系用于分销收益归属。
- 最终公会确认以爬取/后台数据为准。

---

### 2.4 生成自己的分销邀请码

- 用户可以生成自己的分销邀请码。
- 新用户注册分销系统时填写该邀请码。
- 邀请码用于建立上下级关系，并驱动后续裂变人数、收益、提现统计。

验收点：
- 邀请码应固定不变。
- 邀请码应可复制、可打开邀请/绑定入口。
- 邀请码与用户、产品、公会视角应可追溯。

---

### 2.5 收益关系 / 佣金层级

脑图定义的佣金层级如下：

| 脑图层级 | 关系 | 提成比例 | 备注 |
|---|---|---:|---|
| 二级分销 | 下级 / 直接下级 | 10% | 默认规则 |
| 三级分销 | 下下级 | 2% | 临时 |
| 四级分销 | 下下下级 | 0.5% | 临时 |

说明：
- 当前业务口径把用户自己的下级称为“二级分销”。
- 技术实现里通常可映射为 reward level 1 / 2 / 3。
- 产品展示时应使用业务口径：二级、三级、四级。

验收点：
- 收益计算必须支持 3 层上级受益人，对应业务二级/三级/四级。
- 默认比例应按脑图为 10% / 2% / 0.5%。
- 活动期比例提升应可配置。

---

### 2.6 收益时间

- 正常情况下收益永久有效。
- 偶尔做活动时，特定时间内相关比例会提升。

验收点：
- 默认规则无结束时间。
- 活动规则要有生效开始/结束时间。
- 同一层级在活动期应优先命中活动规则。

---

### 2.7 查看裂变数据

裂变数据分为两类：

1. 人数
2. 收益

#### 2.7.1 人数

需要展示：

- 团队总人数。
- 下级多少人。
- 下下级多少人。
- 下下下级多少人。

下级明细需要展示：

- 具体是哪些 ID。
- 下级的总钻石收入。
- 下级上周钻石。
- 下级本周钻石。

验收点：
- 至少支持按 3 层下线统计人数。
- 可查看每层具体用户 ID。
- 至少直接下级要展示总钻石、上周钻石、本周钻石。

#### 2.7.2 收益

需要展示：

- 所有总收益。
- 二级收益。
- 三级收益。
- 四级收益。

二级收益明细需要展示：

- 具体是哪些 ID。
- 下级的总钻石提成。
- 下级上周钻石提成。
- 下级本周钻石提成。

验收点：
- 用户端应按业务二级/三级/四级展示收益。
- 至少直接下级收益要能展开到具体 ID。
- 上周/本周统计要有稳定的时间口径。

---

### 2.8 提现

脑图提现规则：

- 每周只能申请 1 次。
- 1000 钻石起。
- 提现的人才转钻石。

当前解释口径：
- 未申请提现的收益只在分销系统内记录。
- 用户主动申请提现后，系统按可提现钻石生成申请单。
- 后续由运营人工转钻石 / 发放。

验收点：
- 同一用户同一周只能提交一次申请。
- 可提现金额不足 1000 钻石时不能申请。
- 申请后对应奖励要被占用，避免重复申请。
- 后台应能通过/驳回申请。
- 通过后标记已发放；驳回后释放奖励重新可申请。
- 用户端后续应能查看提现记录。

---

## 3. 公会端需求

### 3.1 设置规则

公会端需要支持设置：

1. 提成比例。
2. 收益时间。

验收点：
- 可配置业务二级/三级/四级的比例。
- 可配置永久规则。
- 可配置活动期临时规则。
- 活动期规则支持开始/结束时间。

---

### 3.2 爬取数据

公会端需要爬取 / 同步 Linky 数据，用于：

- 确认所有 Linky ID 的所属公会。
- 判断 Linky ID 是否属于上级对应公会。
- 获取用户钻石收入。
- 获取下级、下下级、下下下级的钻石数据。
- 支撑最终收益计算、裂变统计、报表。

验收点：
- 数据来源需要可追溯。
- 抓取失败需要留痕。
- 最终公会确认要以爬取数据为准。
- 需要支持按公会维度查看/统计。

---

### 3.3 查看报表

公会端报表包括：

1. 每周裂变提现报表。
2. 每个公会的裂变信息报表。

#### 3.3.1 每周裂变提现报表

应包含：

- 申请周期。
- 用户 ID。
- Linky ID。
- 所属公会。
- 申请钻石数量。
- 申请状态。
- 处理时间。
- 处理备注。

#### 3.3.2 每个公会的裂变信息报表

应包含：

- 公会 ID / 公会名称。
- 公会邀请码。
- 分销用户数。
- 团队人数。
- 各层级人数。
- 总钻石收入。
- 总提成。
- 已提现 / 待提现。

---

## 4. 待产品确认的问题

1. 手机号注册是否使用验证码、密码还是第三方登录。
2. Linky ID 是否允许解绑/换绑。
3. “上级对应公会”如何配置：上级用户、公会账号、产品、邀请码之间的映射关系是什么。
4. Linky 公会邀请码由谁提供，用户侧提示从哪里读取。
5. 10% / 2% / 0.5% 的计算基数是 Linky 钻石收入、充值、流水还是净收益。
6. 活动期比例是否按公会配置，还是全平台统一配置。
7. 每周提现的周口径：ISO 自然周还是滚动 7 天。
8. 提现“转钻石”是否只支持人工发放，是否需要导出表。
9. 公会报表是否需要导出 Excel/CSV。
10. 爬取频率、延迟和失败重试规则。
